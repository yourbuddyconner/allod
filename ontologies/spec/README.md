# spec: the specification governing itself

The spec promises (§0.1) that from v1.0 onward, its own change history
will live in an Allod graph. This package is the vocabulary that graph
will use: parts, sections, requirements, the design decisions behind
them, and the test vectors that verify them.

## Contents

| File | Contents |
|---|---|
| [ontology.yaml](ontology.yaml) | Parts, sections, requirements, design decisions, issues, test vectors |
| [taxonomy.yaml](taxonomy.yaml) | Normative vs. informative text, and stability levels |
| [policy.yaml](policy.yaml) | Stricter review for changes to normative text |
| [examples/elision-decision.yaml](examples/elision-decision.yaml) | A real design decision from this spec's history, recorded as graph data |

## Why dogfood

Every claim the spec makes about governed knowledge gets tested against
the most demanding editor available: the spec's own authors. A change to
normative text — the binding "MUST" and "SHALL" parts — requires owner
review and a cooling-off period, and produces a signed approval record
that any implementer can verify. And when someone asks why a section
exists, the answer is in the graph: the section links to a recorded
design decision with its rationale attached.

The link from test vectors to requirements has a practical use. Each
vector declares which requirement it `verifies`, so conformance coverage
becomes a graph query, and a requirement with no test vector pointing at
it is a gap you can list mechanically.
