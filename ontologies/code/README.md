# code: the code-graph ontology

This package defines the vocabulary for graphs built automatically from
source code (spec §8.3). A repository import walks a git repo at a given
commit and proposes
records for its files, modules, functions, and types, with relationships
for imports, calls, references, and implementations.

Everything under this ontology is **derived** — produced by a tool rather
than asserted by a person. Each record carries metadata naming the method
that produced it: `deterministic` for extraction by SCIP, LSIF, or
tree-sitter, or `model-assisted` when a language model was involved.
Model-assisted output faces stricter admission rules (spec §8.2).

Three design rules shape the package:

- **The graph holds hashes, not code.** Records point at git blobs and
  commits through `git:` references. The graph describes the code without
  containing it.
- **One commit, one changeset.** Each imported commit produces exactly one
  batch of changes to the graph. The code graph can therefore be rebuilt
  as of any commit, and comparing the graphs at two commits gives a
  semantic diff — which functions and types changed, not just which lines.
- **Derived and asserted knowledge stay separate.** Derived records can be
  regenerated safely at any time; asserted records are claims made by a
  person or an agent and must not be overwritten by a re-import (spec
  §8.4). Keeping this ontology separate from `corp` and `eng` keeps that
  line sharp.

Tree-sitter extraction is a valid fallback at lower resolution: it fills
in source files and their declarations reliably, but leaves call and
reference relationships sparse.
