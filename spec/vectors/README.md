# Test vectors (Appendix H)

Known-good inputs and their expected hashes, so an independent
implementation can confirm it computes the same results as the reference.
An implementation conforms to the hashing rules when it reproduces every
hash in `vectors.yaml` from `log.yaml` and the ontology packages.

Generated by `cargo run -p allod-vectors -- generate spec/vectors`. Do
not edit by hand; CI regenerates the files and fails on any diff.

## Contents

- `log.yaml` — a three-changeset log in stored form: a first changeset
  with five operations, a second that updates and deletes objects, and a
  third used for the elision vector (elision: removing an operation from
  stored history while keeping the remaining hashes checkable).
- `vectors.yaml` — the expected values: package content hashes, each
  changeset's hash, its operation Merkle root, leaves, and the exact
  bytes that were hashed (hex), the state hash and full state listing
  after each changeset, the elision proof, and an intent redaction (the
  changeset's free-text rationale replaced by its hash).

## How each hash is built

- **Canonical encoding** (§7.1): CBOR per RFC 8949 Core Deterministic
  Encoding — definite lengths, map keys sorted by their encoded bytes,
  integers in shortest form. Map keys are strings. This fixes one exact
  byte sequence for any value, which is what makes the hashes
  reproducible.
- **Domain separation**: every hash is SHA-256 over `allod:<domain>:`
  followed by the payload, rendered as `sha256:<hex>`. The domain prefix
  makes a hash of one kind of thing unusable as a hash of another. The
  domains are `object`, `changeset`, `intent`, `op-leaf`, `op-node`,
  `state-leaf`, `state-node`, and `package`. The one exception is
  document content hashes (§1.5): plain SHA-256 of the file's exact
  bytes, with no prefix, so they match what anyone computes over the
  file with standard tools.
- **Object revision hash** (§1.7): the canonical encoding of the object
  with its `rev` field omitted.
- **Changeset hash** (§3.2.1, §3.2.6): the canonical encoding of the
  changeset with `hash` and `signature` omitted, `operations` replaced
  by the root of the operation Merkle tree, and `intent` replaced by its
  hash. A redacted changeset stores `intent_hash` in place of `intent`,
  but the bytes being hashed are identical either way — which is why the
  changeset hash survives redaction.
- **Merkle trees** (§1.7): binary trees over the leaves in order. An odd
  leftover node is promoted unchanged. Interior hashes are computed over
  the two concatenated raw 32-byte child digests, under the `-node`
  domain.
- **State hash** (§1.7): a Merkle tree whose leaves are the canonical
  encodings of `{kind, id, rev}` for each live object (plus
  `deleted: true` for tombstones), ordered by kind and then by ID.
- **Package hashes** (§2.5): the canonical encoding of the ontology
  package document, hashed under the `package` domain, with the hashes
  of its own imports resolved first. This is the content hash that
  import declarations bind to for now (see
  [ontologies/README.md](../../ontologies/README.md) for the planned
  change), and `allod-lint` verifies every import declaration against it.

## Signatures and the governance audit

Signatures are Ed25519 over the ASCII bytes of the changeset hash, using
the well-known test keys from RFC 8032. The secret keys appear in
`vectors.yaml` because they are deterministic test material — never use
them for a real graph.

The `governance` section replays the same proposal twice under the
`memory-local` policy: two setup changesets establish who holds which
keys, then two approval records that differ only in who signed them. One
passes the policy check and one fails. An implementation must reproduce
both verdicts from the log, the policy, and the keys alone.
